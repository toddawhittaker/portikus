## Goal

A student can see what is using their workspace's CPU and memory and stop their own runaway program from the Monitor pane, is warned before memory runs out, and gets full CPU back on their own once they have been quiet for five minutes. An administrator can see a workspace's heaviest processes, read from Incus rather than from the student-controlled agent, and stop one of the student's programs.

Closes #595, #596, #607.

## Terms

- **The agent:** the workspace agent, which runs inside the container as `student` (uid 1000) in `portikus-workspace-agent.service`.
- **Start ticks:** field 22 of `/proc/<pid>/stat`, the time the process started in clock ticks since boot. A PID plus its start ticks names one process for its whole life, so a reused PID is caught.
- **Short name:** the kernel's 15-character process name (`/proc/<pid>/comm`, or field 2 of `stat`), never the command line.
- **Protected process:** a process no stop path may signal: PID 1, anything not owned by uid 1000, the agent itself, and any process whose short name is `tmux: server`.

## Rulings

### Automatic throttle lift (#596, T1)

1. **The rule.** Each tick the worker judges a throttled workspace for a lift. Only samples taken after the throttle's `at` count. The anchor is the newest such sample at least the lift time old; with none there is no decision yet. The average is computed exactly as the CPU judgement's (the same function, the same restart rule, against the full CPU limit, not the throttled allowance). The throttle lifts when that average is strictly below the lift percent. Reason: reusing the judged average keeps one definition of "busy", and measuring against the full limit matches the issue's "10% of the workspace's CPU limit".
2. **The lift** clears `workspaces.cpu_throttle`, deletes only the samples taken at or before the throttle's `at` (as a stop does), and audits `workspace.cpu_throttle_lifted` with `{reason: "idle", averagePercent}` in one transaction. The same tick's allowance sync removes the Incus allowance. Reason: the issue asks that the rolling window still counts the recent run.
3. **Two platform settings, no per-workspace override:** `settings.cpu_idle_lift_minutes` (1 to 60, default 5) and `settings.cpu_idle_lift_percent` (0 to 100, default 10; 0 turns automatic lifting off). They are edited in the admin Settings tab's Resource guard section as two more fields, and are not keys of `guard_config` or of the per-workspace guard dialog. Reason: the issue asks for no override until someone needs one; 0 as "off" matches the guard's "100 turns a check off".
4. **The student's throttle view carries the lift facts.** `WorkspaceCpuThrottle` gains `idleLiftMinutes` and `idleLiftPercent`, read from the settings row when the view is built, both null when lifting is off. The notice's body adds "It returns to full speed on its own after {minutes} minutes under {percent}% use." when they are set. Reason: the notice's numbers already come from the view.
5. **The student is told of a lift by a toast, not by the server.** When the page sees `cpuThrottle` go from set to null while it is open, it shows the success toast "Your workspace is back to full speed", which the notification history records as every toast is (ADR 0033). The worker writes no notification row. Reason: no new worker write path (Epic 17 is adding one on another branch); a student who was away needs no message about a throttle that is already gone.

### The student's memory flag (#607, T1 and T3)

6. **The student's workspace view gains `memoryFlag`** (`{at, averagePercent, thresholdPercent, windowMinutes}` or null), built as `cpuThrottle` is. SPEC.md 19.4's "the student sees nothing" becomes a notice.
7. **The memory notice** (warning tone, dismissible for the page's life per flag `at`, like the throttle notice) reads: title "Your workspace has been near its memory limit"; body "For {window} minutes it used more than {threshold}% of its memory. If it runs out, the biggest program is stopped." Its action is **See what's using memory**. Reason: the issue's wording, in the throttle notice's shape.

### Stopping a process: the agent (#607, T2)

8. **One agent route serves both the student and the administrator:** `POST /processes/:pid/stop` with body `{startTicks, force}`. The PID is parsed as a positive integer (400 otherwise). The agent reads `/proc/<pid>/stat` and `status` at request time and answers 404 `PROCESS_NOT_FOUND` when the PID is gone, 409 `PROCESS_CHANGED` when its start ticks differ, and 403 `PROCESS_PROTECTED` for a protected process. Otherwise it sends SIGTERM (SIGKILL when `force`), waits up to 3 seconds (the Running pane's grace), and answers 200 `{pid, exited}`, where a zombie or a vanished PID counts as exited. It never sends SIGKILL on its own: `exited: false` is how the browser learns to offer **Force stop**. Reason: one checked path is easier to review than two; the issue asks that Force stop be offered, not automatic.
9. **The agent needs no new privilege.** It runs as the student, so the kernel already refuses anything the student does not own; the protected list stops the agent, the terminals' tmux server and PID 1 being signalled by accident. The student can already kill any of their own processes from a terminal, so the route gives them nothing new.
10. **The tmux server is recognised by its short name `tmux: server`**, not by asking tmux. Reason: it works both with today's own-server tmux and with Epic 16's `portikus-terminals.service`, and it keeps `tmux.ts`, which Epic 16 rewrites, out of this epic. A student's own tmux server (possible after Epic 16) is protected too, which costs nothing: they can stop it from a shell.
11. **The usage sample gains three fields per process:** `startTicks`, `stoppable` (false for a protected process), and `commandLine`, the student's own processes' `/proc/<pid>/cmdline` with NUL bytes as spaces, capped at 1024 characters, and null for anyone else's. The command line is the student's own data shown only to them: it is never logged, never audited, and the admin detail's usage (which already refuses a process list) never carries it. Reason: one sample already feeds Monitor every second; a separate fetch per row would add a route for the same data.
12. **Memory used becomes the working set.** The agent's `memory.usedBytes` subtracts `inactive_file` from `memory.stat` when it reads the cgroup, as the guard does (SPEC.md 19.4). Reason: the status bar warning (ruling 17) must not fire because a large file was read into the page cache.

### Stopping a process: the API (#607, #595; T2 and T4)

13. **Student route:** `POST /workspaces/:id/processes/:pid/stop`, owner-only in `route-policy.ts`, 409 `WORKSPACE_NOT_RUNNING` when not running, one stop at a time per workspace (409 `STOP_IN_PROGRESS`), at most 30 stops per user per minute (429), and the agent's refusal codes passed through. Modelled on `POST /workspaces/:id/listening/:port/stop`.
14. **Administrator route:** `POST /admin/workspaces/:id/processes/:pid/stop`, admin-only, the same body and answers, calling the same agent route. The student gets a notification row written by the API (tone `info`, title "An administrator stopped a process in your workspace", no process name), using the insert and trim of `POST /me/notifications` moved into one function in `routes/notifications.ts`. Reason: the stop only needs the student's own powers, which the agent has; the controller would need a new root-level kill path to do the same.
15. **Audit:** each signal sent writes `workspace.process_stopped` with `{pid, signal, exited}`, actor `user:<id>` for both routes (the actor's role tells student from administrator). Refusals are not audited. No row holds a process name or command line (SPEC.md 24.11).

### The administrator's process list (#595, T4 and T5)

16. **The list comes from Incus through the worker, never from the agent.** Only the worker holds the controller's token (ADRs 0006 and 0022), so the API does not call the controller. The administrator presses **Refresh**: the API upserts a row in the new `workspace_process_snapshots` table (`workspace_id` primary key, `requested_at`, `requested_by`, `taken_at`, `processes` jsonb, `error`) and answers 202. A worker loop, every second, takes each running workspace's pending request, calls the controller's new `GET /instances/:name/processes` with a 10-second timeout, and writes the result or an error code. The browser polls `GET /admin/workspaces/:id/processes` once a second until `taken_at` passes its request, for at most 20 seconds. Rows older than one hour are deleted by the same loop. Reason: a tampered agent could hide a miner; a direct API-to-controller token would widen what a compromised API can do to every instance. This is ADR 0034.
17. **The controller reads `/proc`, not `top`.** It runs one Incus exec as uid 1000 and gid 1000, a fixed POSIX shell command with no caller input, that prints every process's owner uid and `/proc/<pid>/stat` line, sleeps one second, prints them again, and prints the agent's `MainPID` from `systemctl show`. Records are separated by NUL bytes and the output is capped at 4 MiB. The controller computes CPU percent over that second from `utime + stime` against the instance's CPU limit, resident memory from the `rss` field, and returns the top 10 by CPU and the top 10 by memory (their union, at most 20 rows) with PID, uid, short name, start ticks, CPU percent, resident bytes and `protected`. Reason: `top` gives no start ticks for the stop check and its columns vary between procps versions; the one-second sample still gives current CPU, as the issue asks.
18. **The short name is parsed between the first `(` and the last `)` of the stat line**, control characters replaced with `?`, and capped at 15 characters. It is the only text from the workspace that reaches the admin. SPEC.md 20.1's limit (short names, never command lines) holds.
19. **The exec reads its output through Incus's recorded output** (`record-output: true`, then the log files named in the operation's metadata, which the controller deletes afterwards). The other exec calls are unchanged.

### The student interface (#607, T3)

20. **Monitor rows gain a Stop button** (an icon button named "Stop {name} (PID {pid})") only where `stoppable` is true. It opens the same kind of confirmation Running uses: "Stop {name}?" with the PID, and **Stop**. On `exited: false` the dialog stays open and says "{name} is still running." with **Force stop**. Errors show in the dialog in user terms (not found: "That program has already stopped."; changed: "That process ID now belongs to a different program. Refresh and try again."; protected: "Portikus needs this process, so it cannot be stopped here.").
21. **The full command line** shows in a row below the process when its disclosure button ("Show the full command for PID {pid}", `aria-expanded`) is pressed, in the monospace face, wrapping. Only rows with a `commandLine` have the button. The short name cell keeps its `title`. Reason: hover alone is not reachable by keyboard.
22. **Monitor can be opened with a sort.** `rightPane.ts` gains `showMonitor(column)`, which selects the Monitor tab and sets its sort to that column descending; Monitor keeps its sort in the right-pane context instead of local state, so the request survives the tab mount. Reason: both notices and the status bar need it, and the sort already lives in `sort.ts`.
23. **The throttle notice** gains **See what's using CPU** (`showMonitor("cpu")`) beside **Restart workspace…**, and the idle-lift sentence of ruling 4.
24. **The status bar memory warning** appears only when the working set is at or above 85% of the limit: "Memory {used} of {total}" in the warning tone with the alert icon (text, not colour alone), a button that runs `showMonitor("memory")`. Below 85% nothing is shown. It rides the status bar's existing 30-second usage poll and its crossing is announced through the existing status region. Reason: Epic 20 removed the status bar's permanent storage line on purpose (DESIGN.md, "Where the build departs from the mockups"), so memory follows the same warning-only rule.

## Left out

- **Stopping a process tree** (a program and its children together), and renice. The issue leaves them out; Epic 16's `process-tree.ts` is where a tree stop would come from.
- **Any change to the Running pane.** The issue keeps it about ports.
- **Per-workspace override of the idle-lift settings.** The issue asks for none until needed.
- **A repeat limit on the throttle, idle, throttle again cycle.** The issue accepts the gap; the existing BACKLOG entry on a repeat limit covers it.
- **An administrator's stop that does not go through the agent.** If the agent is down the admin cannot stop a process; stopping or restarting the workspace still works. A root-level kill path in the controller is more to secure than this case is worth.
- **Showing the administrator's process list automatically or live.** The issue asks for a Refresh button, which also keeps process names out of the guard's own reads (SPEC.md 19.4).
- **A server-side notification for the idle lift** (ruling 5).
