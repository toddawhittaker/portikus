This is the working brief for Epic 19. It is the requirement an agent implements against. Where it is silent, `docs/SPEC.md` wins on behaviour and `docs/STACK.md` on technology. It serves SPEC.md sections 25.6 (observability) and 24.11 (audit and logging rules), STACK.md section 15, and ADRs 0012 (structured logging) and 0022 (metrics in PostgreSQL).

## Goal

An administrator can see how the platform behaved over the last hour, six hours, day or week on one Health tab: larger charts with axes for the host, the API's traffic and errors, workspace activity and the resource guard. A new Logs tab shows the platform's own ERROR, WARN, INFO and DEBUG lines from the journal, filtered and redacted, so a failure can be diagnosed without a shell on the VM.

## Terms used throughout

- **Journal:** systemd's log store on the VM, read with `journalctl`. Every Portikus service writes pino JSON lines to it (ADR 0012).
- **Bucket:** one slice of time on a chart. Every chart on the Health tab uses the same bucket width for a given range.
- **Range:** the time span the Health tab shows: 1 hour, 6 hours, 1 day or 7 days.

## Rulings

### Charts and the Health tab (#597, #603)

1. **No charting dependency.** Charts are hand-rolled SVG in `apps/web/src/admin/health/charts/`, like today's `Sparkline.tsx`, which they replace. STACK.md names no charting library and every chart here is a line, a bar, a strip or a grid; a library would cost bundle size and a styling fight with the tokens for no gain.
2. **Four fixed ranges and bucket widths:** 1 hour in 1-minute buckets (60), 6 hours in 5-minute buckets (72), 1 day in 15-minute buckets (96), 7 days in 1-hour buckets (168). Samples are one a minute and kept 7 days, so nothing finer or longer is meaningful. The API does the bucketing, so the browser never gets more than 168 points per series. No sliding window (issue #597 allows it later).
3. **Every chart on the tab shares the range's bucket.** Count charts (log lines, guard events, activity) label the bucket ("per hour" at 7 days, "per 15 minutes" at 1 day, and so on). One rule is easier to read than per-chart widths; at 7 days it is exactly Todd's "per hour".
4. **Downsampling:** percentages, load, CPU % and running count use the **maximum** in the bucket, because peaks are what matter for capacity (today's rule). Throughput (network, disk) uses the **average** bytes per second over the bucket. Counts are sums.
5. **The range control** is a `pk-actions` group of four `Button size="sm"` with `aria-pressed`, at the right of the Trends card's heading row (#603). The choice is remembered per browser in `localStorage` under `portikus.admin.healthRange`, read and written inside `try`/`catch`, defaulting to 1 day. It is not in the URL: it is a viewing preference, not a place.
6. **Chart anatomy:** a Y axis with three to five rounded ticks and units; X-axis time labels (clock times for 1 hour to 1 day, weekday and date for 7 days); 0 to 100% for percentages; 0 to a rounded maximum for load with a reference line at the CPU count; threshold lines where the guard or the pool uses one. Plot height about 160 px, charts two per row inside the Trends card at 1280 px and wider, one per row below that.
7. **No new design tokens.** Styling follows #603 item 4 with existing tokens: series `accent`, gridlines and baseline `line`, tick labels `ink-muted` at the caption size with `tabular-nums`, threshold lines `status-warning`, plot area `surface-raised`, readout `shadow-md`. A second or third series in one chart (load 1, 5 and 15 minutes; median and 95th percentile; in and out) uses `ink-muted` with a dash, then a dot, pattern and a legend, so series never rely on colour alone. Error and warning bars use `status-error` and `status-warning`, stacked, with a legend.
8. **Accessibility of charts:** the SVG is `role="img"` with an `aria-label` that is the text summary, and the summary stays visible under each chart ("Now 16%, highest 18%"). The plot sits in one focusable element (one tab stop per chart, named "<label>, use the left and right arrow keys to read values"); left and right arrows move a cursor bucket by bucket, Home and End jump to the ends, and a polite live region reads "14:05, 42%". Hover shows the same readout. On a bar chart that links somewhere, Enter on the selected bar follows its link; bars are not separate tab stops.
9. **Health layout (#603):** row 1 two columns, Platform and Resource guard; row 2 full width, the Trends card (heading "Trends", range control on the right, charts below); row 3 two columns, Failures and Workspaces by state. Columns collapse to one below 1024 px. "Workspaces by state" lists every state in `KNOWN_STATES` order with `WorkspaceStateBadge` (move both to a shared module if importing from `WorkspacesTab.tsx` would make a cycle) and counts right-aligned with `pk-num`, zero counts included, so the list never jumps. The pool warning uses `pk-tag pk-tag--warning`.
10. **Failures stay "last 24 hours".** The Failures table is a fixed-window summary and does not follow the range control; its caption says so. Making it follow the range would change `GET /admin/health`'s counts query for little benefit.
11. **One series route.** `GET /admin/health` keeps the current-state fields and loses `series`. A new admin-only `GET /admin/health/series?range=1h|6h|1d|7d` returns every chart's data in one `HealthSeries` body (contract below), with `cache-control: no-store`. The tab polls it every 60 seconds, the sample rate, and `/admin/health` every 30 seconds as today. The log-count chart is the one exception: it reads `GET /admin/logs/counts` (ruling 27), because the journal is slow and separate from the database.
12. **T1 writes the whole `HealthSeries` contract and stub modules for the other families** (see the task table), so T3a, T3b and T4 each fill only their own files and can run at the same time. A stub returns an empty array or `null`, and its chart component renders nothing. This is the one place the plan accepts scaffolding, because the alternative is serializing three tasks on the same two files.

### The `HealthSeries` contract (T1 writes it; `packages/contracts/src/health-series.ts`)

```ts
HealthRange = z.enum(["1h", "6h", "1d", "7d"])
HealthSeriesQuery = z.object({ range: HealthRange }).strict()
HealthSeries = z.object({
  range: HealthRange,
  bucketSeconds: int positive,
  from: datetime, to: datetime,            // the range's edges, aligned to buckets
  cpuCount: int positive nullable,          // from the newest sample, for the load reference line
  host: array({ at, poolPercent: number, memoryPercent: number,
                load1: number, load5: number, load15: number }),                     // T1
  platform: array({ at, sampleMinutes: int, reachableMinutes: int,
                    runningWorkspaces: number nullable, cpuPercent: number nullable,
                    netRxBytesPerSecond: number nullable, netTxBytesPerSecond: number nullable,
                    diskReadBytesPerSecond: number nullable, diskWriteBytesPerSecond: number nullable }), // T3a
  events: array({ at, throttles: int, memoryFlags: int, idleStops: int, guardLifts: int,
                  starts: int, stops: int, signIns: int }),                            // T3b
  usage: object({ retentionMinutes: int, from: datetime,
                  workspaces: array({ workspaceId: uuid, owner: { id: uuid, displayName: string },
                                      cpuThresholdPercent: number, memoryThresholdPercent: number,
                                      cells: array({ at, cpuPercent: number nullable,
                                                     memoryPercent: number nullable }) }) }), // T3b
  api: array({ at, requests: int, clientErrors: int, serverErrors: int,
               webSocketUpgrades: int, medianMs: number nullable, p95Ms: number nullable }),  // T4
})
```

Buckets with no data are absent from an array, not zero-filled; the chart draws a gap. `bucketSeconds` and `from` let the browser place them. A builder who finds a field unworkable raises it with the orchestrator rather than editing the contract in a parallel task.

### More Health charts (#598)

13. **Load 5 and 15 minutes** are two more lines on T1's load chart (item 1). They are already in every sample.
14. **Availability strip (item 2):** one thin band per bucket, filled by the share of minutes that have a sample (`sampleMinutes / (bucketSeconds / 60)`) and marked where the controller was not reachable (`reachableMinutes` below `sampleMinutes`). Gaps and outages are shown with a pattern as well as `status-error`, not colour alone. Its summary reads "Samples in 1,436 of 1,440 minutes; controller unreachable for 3."
15. **Running workspaces (item 6)** are counted by the **worker** from the database (`workspaces.state = 'running'`) and stored in each `health_samples` row as a new `HealthSample.runningWorkspaces` field (`int nullable`, default `null` for old rows). The controller's instance list includes stopped instances and is stripped from old rows, and the database is the source of truth for state.
16. **Host CPU %, network and disk (items 7, 8)** are measured by the **controller** from `/proc/stat`, `/proc/net/dev` and `/proc/diskstats`, as deltas against its previous reading held in memory. They go into `HostSnapshot` as one new field, `rates: { cpuPercent, netRxBytesPerSecond, netTxBytesPerSecond, diskReadBytesPerSecond, diskWriteBytesPerSecond } | null`, `.default(null)`. The first snapshot after a controller restart has no previous reading and reports `null`; so does a reading whose counters went backwards. The readers live in a new file, `apps/workspace-controller/src/host-rates.ts`, and `host.ts` gains only the call and the field, so the conflict with Epic 17 (below) stays small.
17. **Network counts only the default-route interface** (from `/proc/net/route`), because the bridge and veth interfaces double-count workspace traffic that also crosses it. **Disk counts whole block devices** listed in `/sys/block`, excluding `loop*`, `ram*`, `zram*` and `dm-*`, at 512 bytes a sector, so the thin pool's device-mapper layers are not counted twice.
18. **Per-workspace heat map (item 3):** rows are workspaces with at least one sample in the window, sorted by owner name; columns are buckets of the range, but the window is never longer than `workspace_usage_samples`' retention (245 minutes today), and the chart says "Per-workspace figures are kept for about 4 hours" whenever the range is longer. CPU % is the CPU time delta over the limit's allowance, the same arithmetic as the guard (`apps/worker/src/guard.ts`); memory % is the working set over the limit. A cell is shaded by value in steps of `accent`; at or above the workspace's effective guard threshold (its `guard_config` override, else the settings default) it uses `status-warning` with a hatch. A CPU and Memory toggle (two `Button size="sm"`, `aria-pressed`) picks the measure. Each row's name links to `/admin?tab=workspaces&user=<owner id>`, as the guard list does. Rows are capped at 50 by highest peak; the chart says when it capped. Stopped workspaces have no samples (the worker deletes them at stop), so the map shows running and recently running workspaces only, and says so.
19. **Guard events (item 4)** count, per bucket, `workspace.cpu_throttled` (throttles), `workspace.memory_flagged` (memory flags), `workspace.idle_stopped` (idle stops), and `workspace.cpu_throttle_lifted` plus `workspace.memory_flag_cleared` (lifts). **Activity (item 5)** counts `workspace.start_requested` (starts), `workspace.stop_requested` plus `workspace.idle_stopped` (stops) and `auth.login` with result `ok` (sign-ins). Requests, not the worker's observations, because a request is a person acting. Both queries name their actions so the `(action, at)` index from migration 0014 is used.

### API request metrics (#599)

20. **Totals per minute, not per route.** The charts are the ask, and they show totals; storing a row per route per minute would multiply the table by the number of routes for a breakdown nobody sees yet. A per-route view is in "Left out". Because no route, path, query or ID is stored, the table holds nothing ADR 0012 or STACK.md section 15 forbids.
21. **Table `api_request_samples` (migration `0022_api_request_samples`):** `minute timestamptz primary key`, `requests int`, `client_errors int` (4xx), `server_errors int` (5xx), `websocket_upgrades int`, `latency_buckets int[]` (counts per bucket, same length as the bounds below). Writes are `insert ... on conflict (minute) do update` adding to the existing counts, so a restart within a minute does not lose or double a row.
22. **Latency histogram bounds (ms):** 5, 10, 25, 50, 100, 250, 500, 1000, 2500, 5000, 10000, and one overflow bucket. The median and 95th percentile are computed in the API from the summed buckets of each chart bucket, interpolating linearly inside the bucket that holds the percentile; the overflow bucket reports its lower bound. A bucket with no requests reports `null`.
23. **What is counted:** every HTTP response the API sends, in the same `onResponse` hook family as request logging, except the paths request logging already treats as polling (`/health`). A WebSocket upgrade counts in `websocket_upgrades` only, never in `requests` or latency, so long-lived sockets do not skew response times. The preview authorization subrequests from Caddy are counted like any request; they are real load.
24. **Flush:** the counters live in memory in `apps/api/src/request-metrics.ts`; a timer writes the finished minute once a minute, and the Fastify `onClose` hook writes the partial minute at shutdown. A failed write is logged at warn with the error message only and the minute is dropped, never retried in a loop. **The API prunes** rows older than 7 days after a flush, at most once an hour, keeping the writer and the pruner together (the worker prunes `health_samples` the same way), and keeping this task out of `apps/worker/src/health.ts`, which Epic 17 and T3a both edit.
25. **Charts:** request rate (requests per minute, averaged over the bucket), error rate (4xx and 5xx as a share of requests, two lines), and response time (median and 95th percentile, two lines, milliseconds). WebSocket upgrades are in the request-rate chart's summary, not a line.

### The Logs tab (#476 and its two comments)

26. **Sources:** the journal for `portikus-api.service`, `portikus-worker.service` and `portikus-controller.service` only. (The workspace detail panel's printed command says `portikus-workspace-controller`, which is not the unit's name; T5 removes that command.) The API always passes the three `--unit` arguments itself; no request chooses a unit outside that list.
27. **Access to the journal:** `packaging/systemd/portikus-api.service` gains `SupplementaryGroups=systemd-journal`. The group is given to the API process only, not to the `portikus` user, so the worker (same user) does not get it, and it ships with the package rather than an Ansible `usermod`. The cost, recorded in ADR 0035: a compromised API process can read the whole system journal, including Dex's and Caddy's lines. That is accepted because the API already holds the database, the session secret and the agent tokens.
28. **How the journal is read:** `spawn(JOURNALCTL_PATH, args)` with an argument array, never a shell. `JOURNALCTL_PATH` is a new config setting defaulting to `/usr/bin/journalctl`; e2e points it at a fake. Arguments: `--output=json`, `--output-fields=MESSAGE,_SYSTEMD_UNIT,__REALTIME_TIMESTAMP`, the three `--unit`s, `--reverse` for listing, `--since=@<epoch seconds>` and `--until=@<epoch seconds>` computed by the server from validated dates, `--after-cursor=<cursor>` for paging (the cursor is validated against journald's cursor syntax, `^s=[0-9a-f]{32};i=[0-9a-f]+;b=[0-9a-f]{32};m=[0-9a-f]+;t=[0-9a-f]+;x=[0-9a-f]+$`, and passed as one argument), and `--grep=<pattern>` built only from a fixed map of level names (for example `"level":"(error|fatal|warn)"`) when not every level is selected. User text never reaches an argument: the text, user and workspace filters run in the API after parsing. The builder confirms on the rehearsal VM that `--reverse` with `--after-cursor` walks backwards from the cursor; if it does not, page with `--cursor` and skip the first entry.
29. **Limits:** one request scans at most 20,000 journal entries or 5 seconds, whichever comes first, then kills `journalctl` and returns what it found with a cursor to continue and `scanComplete: false`. At most two `journalctl` processes run at once across the API; a third request gets 429 `RATE_LIMITED` ("Log search is busy. Try again in a moment."). `journalctl` missing, failing or refused permission gives 503 `LOGS_UNAVAILABLE` with a plain message, and the tab shows it (this is also what `pnpm dev` without a journal shows). Page size is 100 lines.
30. **Only Portikus JSON lines are shown.** A `MESSAGE` that does not parse as a JSON object with a string `level`, `service` and `time` is skipped (and counted in `skippedLines` for the tab to mention). Those are systemd's start and stop lines and raw stack traces, which do not follow the "log named fields" rule, so not showing them is the safer default; the tab says to use `journalctl` on the VM for them.
31. **Levels:** the filter offers Error (which includes fatal), Warn, Info and Debug. Error and Warn are on by default. The tab states: "Debug lines exist only while the log level on the Settings tab is Debug. Info lines exist unless it is Warn or Error." (Todd's comment on #476, 2026-09-26.)
32. **Filters:** level, service, time range (last hour, last day, last 7 days, or custom from and to), text, user and workspace. Text is a case-insensitive substring match over the line's `code`, `msg` and `error` fields, at most 200 characters. User matches the line's `userId`. Workspace matches the line's `workspaceId`, or the controller's `instance` field equal to that workspace's Incus instance name, which the API looks up. The filters live in the URL (`/admin?tab=logs&level=error,warn&service=api&since=...&until=...&q=...&user=<id>&workspace=<id>`), so "View logs" links and chart bars can open the tab already filtered and a filtered view can be bookmarked.
33. **Rows:** newest first. Time, level (a `pk-tag` whose text names the level, coloured error or warning where it applies), service, code, message (`error` when present, else `msg`), route, status, user display name and workspace, all from named fields. Display names are resolved with one database query per page for the ids on it; an unknown id shows the short id. Expanding a row (a disclosure button, `aria-expanded`) shows the full line as indented JSON after redaction.
34. **Redaction on display:** `packages/observability` exports one list of sensitive key names used both by the logger's `REDACT_PATHS` and by a new `redactLine(value)` that walks the parsed line to any depth and replaces the value of every key on the list with `"[redacted]"`, and truncates any string longer than 2,000 characters. The API applies it to every line before it leaves the server, for the row fields and the expanded JSON alike. The API sends only the parsed MESSAGE, the unit's service name, the journal timestamp and the cursor, never other journal fields.
35. **Refresh:** the tab refetches every 30 seconds while it is open, as Health does. Once the administrator has loaded older pages with "Load older lines", automatic refresh pauses and a "Refresh" button appears, so the list does not jump under them.
36. **"View logs" links:** the workspace detail panel's "Logs" section replaces the printed `journalctl` command with a "View logs" link filtered to that workspace and the last hour. Each user row's actions offer "View logs" filtered to that user. Removing the command is deliberate: the link does the same job, and OPERATIONS.md keeps the `journalctl` recipe for when the API is down (T7 checks it is there).
37. **Errors per hour on Health (Todd's second comment on #476):** a stacked bar chart of ERROR (with fatal) and WARN lines per bucket over the chosen range, in the Trends card. Each bar opens the Logs tab filtered to that bucket's time span and to the level of the part of the bar the cursor is on (keyboard: Up and Down pick the level in the selected bar). Data comes from `GET /admin/logs/counts?range=` (contract `LogCounts`: `bucketSeconds`, `from`, `to`, `buckets: [{ at, errors, warnings }]`, `complete: boolean`, `oldestAt: datetime nullable`).
38. **How counts stay cheap:** the API keeps per-bucket counts in memory for the last 7 days at one-minute resolution per level, filled by reading only error, warn and fatal lines (`--grep`) forward from the last cursor it read. The first request after an API start reads the whole window once, under the same 20,000-entry and 5-second cap per request, continuing on later requests; until it has caught up, `complete` is false and the chart says "Still counting older lines". Counts older than what the journal still holds (its 2 GB cap, #398) are simply absent, and `oldestAt` lets the chart say where the journal starts.
39. **Audit:** reading logs is not audited. It is a read by an administrator, like the Audit tab, and an audit row per 30-second refresh would be noise.

## Left out

- **A per-route breakdown of API requests** (slowest routes, busiest routes). The charts show totals (ruling 20); a `route` column and a table view are a later migration if needed.
- **A sliding or custom time window on the Health tab.** Four presets cover the stored data (ruling 2); #597 allows the window later.
- **Workspace agent logs in the Logs tab.** They live inside each container, not the VM's journal (#476, "Left out on purpose").
- **Alerts or emails on errors** (#476, "Left out on purpose").
- **Dex, Caddy and PostgreSQL lines in the Logs tab.** Only the three Portikus units are read (ruling 26).
- **Non-JSON journal lines** such as systemd's start and stop messages and raw stack traces (ruling 30).
- **Per-workspace figures beyond about 4 hours.** Longer retention of `workspace_usage_samples` is a separate decision about table size (ruling 18).
- **Sampling faster than once a minute** (#597, "Limits of the data today").
- **OpenTelemetry or a metrics endpoint.** ADR 0022 still holds.
